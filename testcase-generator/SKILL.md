# testcase-generator

## 总体目标

根据需求内容拆分功能模块与功能点，先形成模块级测试用例工作计划，再优先并行生成各模块测试用例，使用等价类、边界值、判定表、错误猜测等方法生成可执行的功能测试用例，并最终导出为 `.xlsx` 文件。

优先生成结构完整、字段统一、能直接交付测试团队的结果，不要只给零散测试点。
默认偏向“多生成、细生成”，不要为了压缩篇幅主动合并场景或省略边界场景。

## 执行流程

按以下顺序工作：

1. 读取需求来源
2. 划分模块与功能点
3. 生成模块级工作计划
4. 优先按模块并行生成测试用例；不支持并行时按计划逐模块生成
5. 自检覆盖率并补漏
6. 输出模块文件与汇总文件

## 第一步：读取需求

支持以下输入：

- 对话中的纯文本需求
- `.md`、`.txt` 文件
- `.docx` 文件

处理规则：

- 直接文本：原样读取后提炼模块、角色、约束、状态流转
- `.md`、`.txt`：直接读取正文
- `.docx`：优先调用 `docx` skill 读取，不要假设固定路径

如果需求存在明显缺口，先列出缺失项，再基于合理假设继续生成；不要因为少量模糊点就停止工作。

如果输入文档很大，不要把整份需求一次性搬进当前上下文反复处理，先做模块索引，再按模块或按章节分批读取。

## 第二步：划分模块

先输出模块清单，再进入详细生成。模块通常来自：

- 一级标题或章节
- 用户角色
- 业务对象
- 独立页面或独立操作流

拆分原则：

- 一个功能点只验证一个主要业务目标
- 增删改查、导入导出、审批流、状态流转应拆开
- 多入口登录、多角色操作、多状态分支应拆成独立功能点
- 页面展示、字段回填、按钮显隐、跳转、新标签打开、下载/打印、配置开关，也应视为独立功能点或子功能点
- 同一功能点中如果同时存在“输入校验”“业务校验”“结果展示”“后端落库”“消息通知”，应继续细拆，不要合并成一条笼统用例

拆分后必须先生成模块级工作计划，再进入用例生成。计划用于约束并行或串行执行，避免不同模块重复生成、遗漏依赖或输出格式不一致。

每个模块计划至少包含：

- 模块名称
- 需求来源范围或对应模块文件
- 功能点清单
- 依赖角色、状态、数据或前置模块
- 适用设计方法，例如等价类、边界值、判定表、错误猜测
- 输出 JSON 文件名
- 是否可并行生成；只有不存在前置顺序依赖时才标记为可并行，数据、角色、状态等只读依赖不阻塞并行

如果需求很大，默认仍然按模块计划推进；优先尝试为互不依赖的模块调用子 agent 并行生成测试用例。当前环境不支持子 agent、权限不足、子 agent 失败或输出缺失时，按同一份工作计划回退为逐模块串行生成。

子 agent 并行生成时遵循以下规则：

1. 每个子 agent 只处理一个模块或一个明确子模块
2. 子 agent 输入必须包含模块需求片段、模块范围、全局字段规范和输出 JSON 路径
3. 子 agent 只输出模块级 JSON，不生成 Excel
4. 主流程负责校验模块 JSON、补漏、合并和导出 Excel
5. 存在依赖关系的模块不得盲目并行，先生成被依赖模块，再生成依赖模块

子 agent 不可用时，仍按模块级工作计划逐个模块生成，并在每个模块完成后立即落盘为模块级 JSON。

对大文档执行以下硬规则：

1. 先只抽取目录、标题、模块名、角色、状态词、业务动作词，形成模块索引
2. 不要在同一轮里同时展开全部模块细节
3. 根据模块索引生成模块级工作计划
4. 不要在同一轮里同时展开全部模块细节
5. 每次只处理一个模块或一个较小章节；互不依赖的模块可交给子 agent 并行处理
6. 当前模块生成完成后立即落盘为模块级 JSON
7. 清空当前模块细节，只保留模块索引、工作计划与必要的全局规则，再继续下一个模块
8. 全部模块完成后再合并为总 JSON，并导出最终 Excel

如输入是超大 `.txt` 或 `.md` 文档，优先先执行：

```bash
python "<skill_dir>/scripts/split_requirements.py" "<input_file>" "<output_dir>"
```

该脚本会输出模块索引 `module_index.json` 和拆分后的模块文本文件，后续只读取当前模块文件生成用例。

## 第三步：按计划生成模块用例

先根据模块清单生成工作计划，再执行生成。工作计划建议使用以下结构：

```json
[
  {
    "module": "登录模块",
    "source": "modules/login.txt",
    "functions": ["账号密码登录", "短信验证码登录"],
    "dependencies": ["用户账号", "验证码服务"],
    "methods": ["等价类", "边界值", "错误猜测"],
    "output": "modules/login.json",
    "parallel": true
  }
]
```

生成策略：

1. 如果可以调用子 agent，将互不依赖的模块计划并行分发给子 agent
2. 如果子 agent 不可用、执行失败或返回格式不合格，使用主流程按工作计划串行生成对应模块
3. 如果某个模块依赖另一个模块的枚举、状态或基础数据，先完成被依赖模块
4. 每个模块生成后立即写入计划中的模块 JSON 文件
5. 不要因为采用并行生成而跳过主流程的字段规范、覆盖补漏和合并校验

每个模块都执行以下动作：

1. 提取功能点、输入字段、角色、状态、依赖数据
2. 用等价类与边界值覆盖字段级校验
3. 对多条件业务逻辑使用因果分析或判定表
4. 用错误猜测补充高风险场景
5. 补齐数据校验、权限校验、状态校验、并发校验
6. 复查是否还有“显隐、跳转、回填、刷新、返回、打开新标签、下载、打印、配置生效”类遗漏场景

生成时遵循以下硬规则：

- 每个功能点都要有正向和反向场景
- 不要把多个业务功能塞进同一个用例
- 文本输入字段优先考虑空值、格式错误、长度越界、特殊字符、SQL 注入、XSS
- 涉及权限的功能至少包含未登录访问和越权访问
- 涉及状态流转的功能至少包含合法流转和非法流转
- 涉及保存、编辑、删除、提交、导出时，补充数据持久化或结果落库校验
- 涉及库存、余额、提交按钮、异步接口时，补充并发或重复提交场景
- 每个必填字段至少拆出：空值、合法值、格式错误或业务非法值
- 每个有长度或范围约束的字段至少拆出：下边界前一位、下边界、上边界、上边界后一位
- 每个下拉、单选、状态、认证等级、角色类型，都要至少覆盖每个有效取值各 1 条用例
- 每个按钮、链接、快捷入口、面包屑、返回、查看证明、下载、打印、新标签打开，至少覆盖可点击成功和不可点击/不显示或条件受限两类场景
- 每个“只读/不可编辑/自动回填/脱敏显示/默认值显示”要求，至少生成 1 条独立验证用例
- 每个“可配置”要求，至少生成 1 条配置生效用例；如果同时存在启用/停用，至少各 1 条
- 若需求中出现“暂不显示”“当前版本不做”“后续版本开放”，生成显隐控制或版本控制用例，不要忽略
- 对于列表页，至少覆盖查询条件、默认值、空结果、结果展示、操作列、翻页或排序中的适用项
- 对于详情/进度页，至少覆盖节点展示、时间展示、文案展示、按钮显隐、跳转行为中的适用项
- 如果生成后感觉偏少，优先继续补充不同角色、不同认证等级、不同状态、不同入口、不同配置开关、不同返回路径、不同异常提示、不同结果展示形式
- 每个功能点至少生成 1 条 `Low` 优先级用例；典型 Low 场景包括：次要提示文案展示、非核心字段的默认值或占位符显示、低频操作的成功路径、UI 细节（列表截断、换行、字段对齐）、非阻断性的友好提示；不要让某个功能点的所有用例都是 High 或 Medium

### 生成倾向

优先写“细粒度独立用例”，不要写“覆盖多个检查点的大而全用例”。

优先示例：

- 验证缴费单号为空时提交失败
- 验证缴费单号长度超过 21 位时提交失败
- 验证缴费单号自动转大写
- 验证缴费单业务类型不匹配时提示错误
- 验证校验通过后进入预览页

避免示例：

- 验证犯罪证明申请功能正常与异常流程

详细分析方法见：

- `references/analysis-guide.md`
- `references/test-case-fields.md`

## 第四步：字段与输出约束

默认使用以下列头，顺序不可变：

`功能模块, 用例编号, 功能点, 用例标题, 优先级, 前置条件, 测试步骤, 预期结果, 设计人, 执行结果, 执行人, 备注`

字段要求：

- `功能模块`：与模块名保持一致
- `用例编号`：默认按模块缩写连续编号，例如 `LOGIN_001`、`USER_001`、`ORDER_001`
- `功能点`：单一功能点名称
- `用例标题`：简洁表达“做什么 + 条件 + 结果”
- `优先级`：使用 `High`、`Medium`、`Low`
- `前置条件`、`测试步骤`、`预期结果`：允许多行文本
- `设计人`、`执行结果`、`执行人`、`备注`：默认留空字符串，不自动填充

不要擅自切换为别的字段体系，除非用户明确指定。

## 第五步：输出策略

默认输出顺序：

1. 先给出模块识别结果
2. 给出模块级工作计划
3. 优先并行生成模块 JSON；不支持并行时按工作计划逐模块生成
4. 校验各模块 JSON，失败模块回退串行补生成
5. 合并总 JSON
6. 最终输出 Excel 文件路径与用例总数

输出格式规则：

- Markdown：仅用于中间预览或评审，不作为最终交付物
- JSON：仅用于模块暂存、合并和脚本处理，不作为最终交付物
- Excel：最终交付格式，必须生成

模块 JSON 合并前先检查：

- 文件是否存在且为合法 JSON
- 是否为用例数组
- 是否包含固定列头对应的全部字段
- `功能模块` 是否与工作计划中的模块一致
- `用例编号` 是否为空或重复
- 是否明显生成了其他模块的用例

发现缺失模块、空数组、非法 JSON、字段不完整或跨模块污染时，优先按工作计划串行重生成该模块，再参与合并。

如果已按模块写出多个 JSON 文件，再调用：

```bash
python "<skill_dir>/scripts/merge_cases.py" "<modules_dir>" "<output_dir>/all_cases.json"
```

如果当前上下文里已经汇总完成，则直接写出统一 JSON，无需重复合并。

无论中间是否展示 Markdown，都必须在最后执行 Excel 导出，并明确告知生成文件的绝对路径。

Excel 生成命令：

```bash
python "<skill_dir>/scripts/generate_xlsx.py" "<all_cases.json>" "<output.xlsx>"
```

或：

```bash
python "<skill_dir>/scripts/generate_xlsx.py" --merge "<modules_dir>" "<output.xlsx>"
```

## 第六步：质量自检

生成后至少检查以下内容：

- 每个模块都有用例，不遗漏章节
- 每个功能点至少有 1 条正常场景
- 关键字段具备空值、非法值、边界值
- 复杂规则具备组合场景
- 高风险功能具备权限、安全、并发或状态异常场景
- 用例标题不是“测试1”“场景1”这类空泛命名
- 测试步骤可执行，预期结果可验证
- Excel 列头与用户要求一致
- 最终已经产出 `.xlsx` 文件，而不是只停留在 Markdown 或 JSON
- 大文档场景下，是否采用了“模块索引 -> 模块级工作计划 -> 并行或串行生成 -> 模块落盘 -> 最后合并”的流程
- 是否存在把多个校验点合并到一条用例里的情况；若有，优先拆开
- 是否遗漏了显隐、跳转、默认值、只读、脱敏、回填、下载、打印、新标签打开这类细节验证
- 是否每个模块都包含 `Low` 优先级用例；若某模块全为 High/Medium，优先补充展示文案、默认值展示、低频路径、UI 细节等 Low 场景

## 脚本

- `scripts/generate_xlsx.py`：把 JSON 用例导出为 `.xlsx`
- `scripts/merge_cases.py`：合并模块级 JSON 为总表
- `scripts/split_requirements.py`：把超大需求文档切分为模块文件和索引文件

生成 Excel 依赖 `openpyxl`。若环境缺少依赖，明确告知用户安装命令，不要假装已经成功导出。
